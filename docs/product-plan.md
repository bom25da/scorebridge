# Scorebridge 제품 기획

- 작성일: 2026-10-10
- 상태: 초기 기획안
- 제품 형태: 웹 기반 이미지 악보 변환 서비스
- 개발 순서: 인식 엔진 검증 → 웹 PoC → 수정 기능을 포함한 MVP → 사용자 검증

## 1. 제품 목표

Scorebridge는 이미지·PDF 악보를 편집 가능한 디지털 악보로 변환한다. 사용자는 원본과 변환 결과를 비교하고 인식 오류를 수정한 뒤 MusicXML을 내려받아 악보 편집 프로그램에서 작업을 이어간다.

초기 대상은 인쇄 악보를 디지털로 옮기는 연주자와 음악 강사다. 핵심 가치는 단순한 파일 변환이 아니라, 직접 악보를 입력하는 시간을 줄이는 것이다.

초기 제품 가설:

- 선명한 인쇄 단선율 악보에서는 기존 OMR 엔진으로 충분히 유용한 초안을 만들 수 있다.
- 원본 비교와 기본 오류 수정 기능이 있으면 직접 입력보다 완성 시간이 짧아진다.
- 사용자는 인식률 수치보다 실제 수정 시간과 내보낸 파일의 호환성에 가치를 둔다.

## 2. 범위

| 항목 | 웹 PoC | MVP |
| --- | --- | --- |
| 입력 | JPG, PNG, PDF | 동일 |
| 악보 | 선명한 인쇄 단선율 | 단선율, 피아노는 평가 통과 시 추가 |
| 페이지 | 단일 페이지 우선, 이후 최대 5페이지 | 작업당 최대 5페이지 |
| 출력 | MusicXML | 수정된 MusicXML |
| 미리보기 | 디지털 악보 렌더링, 원본 비교 | 동일, 선택한 마디 비교 지원 |
| 재생 | 선택 기능 | 기본 재생과 정지 |
| 수정 | 외부 악보 편집기로 검증 | 음높이, 길이, 쉼표, 임시표의 기본 수정 |
| 작업 관리 | 현재 작업 상태 | 로그인, 개인 작업 이력, 삭제, 실패 페이지 재시도 |

초기 제외 범위:

- 손글씨, 타브 악보, 관현악 총보, 복잡한 현대 기보
- 오디오를 악보로 변환하는 기능
- 범용 악보 편집기 수준의 레이아웃·조판 편집
- 공동 편집, 공개 악보 공유, 결제
- 자체 딥러닝 모델 학습

MIDI와 인쇄용 PDF 출력은 후속 기능이다. 초기에는 악보 정보를 보존하는 MusicXML을 우선한다. 가사·코드·강약 등 부가 기호는 보존 여부를 평가하되 지원 품질을 보장하는 범위에 포함하지 않는다.

## 3. 사용자 흐름과 화면

### 업로드

1. 사용자가 이미지 또는 PDF를 선택한다.
2. 파일 형식·용량·페이지 수를 확인한다.
3. 페이지 썸네일에서 변환할 페이지를 선택한다.
4. 지원 범위를 확인하고 변환을 시작한다.

초기 제안 제한은 파일 20MB, 최대 5페이지다. 서버 부하 시험 이후 조정한다. 암호화된 PDF와 읽을 수 없는 파일은 명확한 이유와 함께 거절한다.

### 변환 진행

- 작업 상태: 대기 → 처리 중 → 완료 / 일부 완료 / 실패
- 페이지 상태: 대기 → 전처리 → 인식 → 검증 → 완료 / 실패
- 실제 상태와 완료 페이지 수를 표시한다. 근거 없는 진행률이나 남은 시간은 표시하지 않는다.
- 브라우저를 새로 고쳐도 작업 ID로 상태를 다시 조회한다.
- 실패한 페이지가 있어도 성공한 페이지는 검토·다운로드할 수 있다.

### 결과 검토

- 넓은 화면에서는 원본과 결과를 나란히 표시한다.
- 작은 화면에서는 원본·결과 탭을 전환한다. 세밀한 편집은 데스크톱을 우선한다.
- 페이지 이동과 확대·축소를 제공한다.
- MVP에서는 결과의 마디를 선택하면 대응하는 원본 영역을 표시한다.
- 박자 합계 등의 규칙 검사를 통과하지 못한 마디를 표시한다.
- 사용자는 기본 수정 후 MusicXML을 내려받는다.

원본 영역 대응은 별도 기술 검증이 필요하다. MusicXML만으로 원본 이미지 좌표를 충분히 얻을 수 없다면 엔진의 중간 결과를 활용한다. 대응이 불가능한 경우 페이지 비교를 제공하고 마디 연동은 후속 기능으로 조정한다.

## 4. PoC 검증 계획

### 구현할 것

- 업로드 및 PDF 페이지 이미지 변환
- 필요 시 회전·기울기 보정과 기본 이미지 정리
- OMR 실행을 위한 비동기 작업 처리
- MusicXML 생성, 파싱 및 구조 검사
- 브라우저 악보 미리보기, 원본 비교, 다운로드
- 페이지별 처리 시간·실패 단계·엔진 버전 기록

전처리는 원본과 비교하여 실제 품질 개선을 확인한 항목만 기본 적용한다. 오선이나 음표를 손상시키는 과도한 필터링은 피한다.

### 엔진 전략

첫 검증 후보는 Audiveris다. 상용 채택은 품질·운영 비용·라이선스 검토를 통과한 뒤 결정한다. 인식 엔진을 교체할 수 있도록 어댑터 뒤에 둔다.

- 입력: 페이지 이미지, 인식 옵션
- 출력: MusicXML, 엔진 버전, 처리 시간, 진단 정보, 가능할 경우 원본 좌표
- 엔진 고유 오류를 서비스의 오류 코드로 변환한다.
- 평가에 사용할 엔진 버전을 고정하고, 버전 변경 시 동일한 자료로 재평가한다.

Audiveris는 AGPL-3.0이다. 상업적 사용 가능 여부와 소스 제공 의무는 별개다. 배포·수정·서비스 결합 방식에 따른 의무를 상용화 전에 검토한다. 별도 프로세스로 실행하는 것만으로 라이선스 문제가 해결된다고 가정하지 않는다.

### 평가 데이터

권리를 확보한 악보 약 60페이지를 준비한다.

| 그룹 | 페이지 수 | 용도 |
| --- | --- | --- |
| 선명한 인쇄 단선율 | 30 | 초기 지원 범위 평가 |
| 선명한 인쇄 피아노 | 20 | 지원 확장 가능성 평가 |
| 스마트폰 촬영 | 10 | 기울기·그림자·흐림의 영향 평가 |

가능하면 직접 만든 MusicXML을 렌더링해 정답 쌍을 확보하고, 허가받은 실제 스캔·사진도 포함한다. 합성 이미지와 실제 입력의 결과는 별도 집계한다. 여러 페이지가 같은 곡에 속하면 설정 튜닝용과 최종 평가용으로 나눌 때 곡 단위로 분리한다.

원본, 정답 MusicXML, 데이터 권리 근거, 악보 유형, 엔진 결과를 추적한다. 권리가 불명확한 악보는 평가·학습 자료로 사용하지 않는다.

### 측정 기준과 진입 목표

아래 수치는 예상 성능이나 제품 홍보 수치가 아니라 초기 의사결정 목표다. 지원 대상 그룹에서 평가하며 어려운 입력과 평균을 섞지 않는다.

| 지표 | 정의 | 초기 목표 |
| --- | --- | --- |
| 변환 완료율 | 유효하게 파싱되고 화면에 표시되는 결과를 만든 페이지 / 평가 페이지 | 95% 이상 |
| 음표 정확도 | 정답과 정렬된 음표 중 음높이·길이가 모두 맞는 비율 | 98% 이상 |
| 무수정 마디 비율 | 핵심 음악 정보에 수정이 필요 없는 마디 / 전체 마디 | 90% 이상 |
| 수정 시간 | 결과를 정답으로 고치는 시간, 직접 입력 시간과 비교 | 50% 이상 단축 |
| 처리 시간 | 지정한 서버·동시성에서 페이지 처리 시간 | 중앙값 60초 이내 |

음표 정확도만으로 삽입·누락을 숨기지 않도록 누락률·추가 음표율 및 삽입·삭제·치환 기반 기호 오류율도 함께 기록한다. 무수정 마디 판정은 음높이, 길이, 쉼표, 성부, 조표·임시표, 박자표를 포함한다. 처리 시간은 큐 대기와 실제 처리 시간을 분리하고 상위 지연값도 기록한다.

PoC의 수정 시간은 외부 편집기로 측정하고, MVP에서는 서비스 내 수정으로 다시 측정한다. 직접 입력과 수정 비교는 같은 난이도의 악보, 같은 도구 숙련도를 기준으로 한다.

### 단계 종료 판단

- 통과: 단선율 기준을 충족하고 오류 수정이 직접 입력보다 빠르다 → MVP 진행.
- 조건부: 특정 유형에서만 좋다 → 지원 범위를 명시적으로 좁히고 진행.
- 미달: 변환은 되지만 수정 비용이 높다 → 엔진·전처리를 비교한 뒤 재평가.
- 피아노 지원: 단선율과 별도로 평가하고 통과할 때만 제품 지원에 포함.

## 5. MVP 요구사항

### 필수

- 사용자별 접근 제어와 개인 작업 이력
- 최대 5페이지 업로드와 페이지 선택
- 비동기 변환, 새로고침 후 상태 복구
- 원본·디지털 악보 비교와 기본 재생
- 음높이·길이·쉼표·임시표 수정, 실행 취소·다시 실행
- 수정 내용 저장 및 재접속 시 복구
- 박자 합계 검사와 문제 마디 표시
- MusicXML 다운로드 및 외부 편집기 호환성 확인
- 실패 페이지 재시도, 작업 삭제, 보관 기간 만료 처리

박자 합계 검사는 못갖춘마디와 성부를 고려한다. 검사 통과를 악보 전체의 정확성 보증으로 표시하지 않는다. 엔진이 보정된 신뢰도 정보를 제공하지 않는다면 임의의 정확도 점수를 노출하지 않는다.

### 완성 기준

- 지원 악보에서 업로드부터 수정된 MusicXML 다운로드까지 완료한다.
- 다운로드한 결과를 MuseScore Studio 등 지정한 편집기에서 열 수 있다.
- 새로고침·중복 요청·실패 재시도로 작업이 불필요하게 중복 실행되지 않는다.
- 일부 페이지 실패가 성공한 페이지 결과를 잃게 하지 않는다.
- 삭제된 작업의 원본·중간 파일·결과 파일이 보관 정책에 따라 제거된다.
- 다른 사용자의 작업과 파일에 접근할 수 없다.

## 6. 기술 구조

```text
웹 화면 → API → 파일 저장소
              → 작업 큐 → 인식 워커
                          → 페이지 변환·전처리
                          → OMR 어댑터
                          → MusicXML 검사·결과 저장
웹 화면 ← 상태 조회·결과 조회
        → 악보 표시·수정·다운로드
```

구현 후보:

- 프런트엔드: React + TypeScript
- API: TypeScript 기반 서버, 구체적인 프레임워크는 구현 시작 시 결정
- 인식 워커: 엔진 실행 환경을 포함한 별도 컨테이너
- 작업 큐: Redis 기반 큐 후보, PoC에서는 최소 구성으로 검증
- 메타데이터: PoC는 가벼운 저장소, MVP는 PostgreSQL 후보
- 파일: PoC는 로컬 디렉터리, 배포 시 비공개 객체 저장소
- 악보 표시·재생·편집: MusicXML 렌더러와 음악 데이터 모델의 호환성·라이선스를 검증한 뒤 채택

렌더러가 편집·재생까지 제공한다고 가정하지 않는다. MusicXML을 서비스의 편집 모델로 읽고 수정 후 다시 내보낼 수 있는지 먼저 작은 기술 검증을 수행한다. 왕복 변환에서 지원 기호와 성부 정보가 손실되지 않는지 확인한다.

초기 저장 모델은 Job, Page, Artifact로 구성한다. Job에는 소유자·상태·엔진 버전·생성/만료 시각을, Page에는 상태·처리 단계·시간·오류 코드를, Artifact에는 원본·결과·수정본의 저장 위치와 버전을 기록한다. 수정본은 원래 인식 결과와 구분해 복구할 수 있게 한다.

## 7. 파일 처리와 운영

- 확장자뿐 아니라 실제 파일 형식을 검사한다.
- 파일 용량, 이미지 픽셀 수, PDF 페이지 수, 워커 메모리와 실행 시간을 제한한다.
- 파일과 작업은 비공개로 저장하며 권한 확인 후 내려받는다.
- 업로드 파일명을 명령 문자열에 넣지 않고 엔진을 인자 배열로 실행한다.
- MusicXML 파싱 시 외부 엔티티와 외부 리소스 접근을 비활성화한다.
- 오류 로그에 악보 내용과 파일 다운로드 주소를 불필요하게 남기지 않는다.
- 초기 보관 기간은 7일을 제안하며, 사용자가 즉시 삭제할 수 있게 한다.
- 업로드 악보를 학습 데이터로 사용하는 기능은 기본적으로 제공하지 않는다.

## 8. 일정과 실행 순서

개발자 1명 기준의 추정이다. 엔진 품질과 편집 모델의 난이도에 따라 조정한다.

| 단계 | 예상 기간 | 산출물 |
| --- | --- | --- |
| 엔진·편집 모델 기술 검증 | 3~5일 | 샘플 변환, 권리·라이선스 기록, 렌더링·왕복 변환 확인 |
| 웹 PoC | 1~2주 | 로컬 실행, 업로드·변환·비교·다운로드 |
| 평가 및 범위 결정 | PoC 기간 내 병행 | 그룹별 품질·수정 시간·처리 시간 보고 |
| MVP | 추가 3~5주 | 기본 편집, 재생, 계정·이력, 재시도, 배포 |
| 사용자 검증 | 1주 | 실제 작업 완료 시간과 실패 유형, 다음 우선순위 |

첫 구현 순서:

1. 권리를 확보한 단선율 샘플과 정답 MusicXML을 준비한다.
2. 고정 버전 엔진으로 단일 페이지를 변환하고 결과를 외부 편집기에서 연다.
3. 브라우저 렌더링과 기본 편집·재출력 가능성을 검증한다.
4. 업로드·비동기 처리·상태 조회·다운로드를 연결한다.
5. PDF와 여러 페이지 처리, 실패 진단을 추가한다.
6. 평가 자료 전체를 실행하고 MVP 진입 여부를 판단한다.

## 9. 위험과 결정이 필요한 항목

| 항목 | 대응 또는 결정 기준 |
| --- | --- |
| 인식 정확도 부족 | 실제 악보 평가 후 지원 범위 축소 또는 엔진 교체 |
| 기본 편집 기능의 구현 규모 | 렌더링과 편집을 구분하고 초기 기술 검증으로 범위 확인 |
| AGPL 의무와 비공개 서비스 계획 | 상용 채택 전 구체적인 통합 방식 검토, 필요 시 다른 엔진 선택 |
| 원본 마디 좌표 확보 | 엔진 중간 결과 검증, 불가능하면 페이지 비교부터 제공 |
| 악보·평가 데이터 권리 | 자작·허가·이용 조건이 확인된 자료 사용 |
| 처리 시간·동시 작업 비용 | 제한된 워커 동시성으로 측정하고 큐·페이지 제한 조정 |

개발 시작 시 결정할 항목은 구체적인 API 프레임워크, 악보 렌더링·편집 라이브러리, 배포 환경이다. 피아노 지원 여부와 최종 엔진은 PoC 결과로 결정한다.

## 10. 비교 제품 및 참고 자료

- [Audiveris](https://github.com/Audiveris/audiveris): 초기 엔진 후보, 라이선스와 MusicXML 출력 확인.
- [Soundslice](https://www.soundslice.com/sheet-music-scanner/): 웹 업로드·원본 비교·편집·내보내기 흐름 참고.
- [ScanScore](https://scan-score.com/en/products/): 인식 결과 수정과 MusicXML 출력 흐름 참고.
- [SmartScore](https://www.musitek.com/smartscore-pro.html): 설치형 OMR·편집 제품 비교.
- [PhotoScore](https://www.neuratron.com/photoscore.htm): 인쇄·손글씨 인식 제품 비교.

제품 광고의 정확도 수치를 Scorebridge의 예상 성능으로 사용하지 않는다. 동일한 평가 자료에서 측정한 결과로 엔진과 제품 범위를 결정한다.
